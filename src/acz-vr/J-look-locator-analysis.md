# J-look-locator: why run B (ee-look-write-run1) did not lock the look block, and a bounded fix

Read-only analysis of `research/experiments/ee-look-write-run1/logs-final/ee-camera.log` against `ee-probe-live-run4`. Nothing run, built or edited. Log times are ms since boot; the sweep (21:17:29.6-21:17:40.8) maps to about 13586.3-13597.0 s in the log (21:17:00 is about 13554.3).

## Established (quoted from the logs)
1. The block WAS found, early, and by the same structure as run 4. Scan 1 (13569473, about 4 s after cockpit entry) ranked `1f8a72e0000+FDD410` rank 0, score 5 (`sane+yaw+vert+horiz+eye`, `eye-err=0.06219@x16`). The same line appears in 17 of the 18 scans (scans 1-3 and 5-18). Run 4 has `240a00fc000+FDD410` score 5 too. Every `scan-full` shift is identical in both runs (404F8, C7BBC, C83C0, CC3BC, 802A78, D27A2C, DAFCA8, F02C60), so offsets inside the 64 MiB region are launch-independent; only the region base moves. `observe-base ... base == region lo` in both runs: base is the region start and `0xFDD410` looks like a fixed PS2 address (not proven to be an address, only that it is stable across 2 launches).
2. The probe DID see the look in run B. Timeline slot 0 (`1f8a72e0000`): `L=0,2.45737,0` (13586565), `L=0,-2.37035,0` (13588882), `L=0,-2.48287,0`, then decay to `-0.0189`, `-1.07e-05`. The writer progressed `no-tracks-look-candidate` -> `candidate-evidence-weak` (13586566, first look sample) -> `look-not-neutral` (13588883, right hold) -> `look-write-settle;base=1f8a72e0000;samples=78;look=9/9` (13589918). Evidence thresholds (>=40 samples, >=6 events, >=80 %) were met with 9/9 hits.
3. The lock was destroyed by one scan. Scan 4 (`13590905`, ms=3690, so it ran about 13587.2-13590.9, i.e. across the RIGHT hold) had `full=9` (others 10) and its `scan-best` was 3 junk entries, all score 4 (`DAFCA8`, `F02C60`, `D27A2C`), with `FDD410` absent. `scan-done` (13590916) -> `observe-follow;base=1f8a70b2898;score=4` + `timeline-candidate;slot=0;base=1f8a702a61c;src=best2` -> `look-write-settle-reset;reason=identity-changed` (13590916.325, 1.0 s into the 3 s settle). `set_tracks` (ee_camera_probe.cpp:700-745) keeps only slots whose eff is in this scan's top 3, so slot 0 (`1f8a72e0000`) was replaced and its counters (9/9) were discarded. Afterwards `look=0/4` on slot 0 and `0/13` on slots 1-3: the up/down holds were counted on junk.
4. Scan 5 (`13597869`, after the sweep) found `FDD410` score 5 again and re-added slot 0 (`observe-follow;base=1f8a72e0000`), but with fresh counters and no further look events, so tracking says `class=noise;look=0/0;quiet-changes=24..422` for the rest of the run, and the writer waits `no-tracks-look-candidate` until `look-write-result;result=aborted;reason=factory-final-release;writes=0`.
5. Likely mechanism of the one miss (strongly supported, not directly logged because the dropped hit is not printed): the scan applies `relations(v,basis,0,0,...)` (ee_camera_scan.cpp:122) with a hard yaw tolerance `|wrap(C-(H+L))| <= 2e-3` (line 44) on a block read non-atomically by a ~3.7 s background pass, and `full` requires sane+yaw+vert+horiz. While L is ramping the composed yaw lags L by a frame. Residuals from the logged timeline rows: 13586565 L=2.45737, rot=1.67591 vs H+L=1.67197 -> 0.0039; 13588882 L=-2.37035, rot=3.11045 vs wrapped 3.12744 -> -0.017; 13589650 L=-0.255175, rot=-1.0023 vs -1.04057 -> 0.038. All exceed 2e-3; at rest it is 0 (`yaw-res=0` in every other scan). Run 4 shows the same event: `observe-follow;base=2409fece898;score=4` at 22:42:46.7, during sweep 2 (`2409fece898` = `240a00fc000+DAFCA8-FDD410`, the same junk). So the fault is deterministic in kind: any scan whose read of this chunk lands in a ramp loses the block.
6. Skip-intro mod (XINPUT1_4, 8x for 60 s) is not implicated by the logs: scan 1 matches run 4 (same offset, score, eye-err, L=0, H=-0.7854), L saturates at the same +-2.48, and the miss coincides with a hold, not with the first minute. Also the sweep was about 4:52 after launch 2 (21:12:37) and 20 s after cockpit entry (cockpit-ms=20649 at scan 4 start), not 2 minutes. Not shown: that the mod has no effect on frame timing.
7. Three junk entries are permanent score-4 passes (`L=1;H=7.0955e-39;air=46.4492,-1.25391,1.25391`; `L=0;H=1;...`): constants, `eye-err=585.5`, no eye match. They occupy slots 1-2 from scan 1 and become `best0` whenever the real block drops out.
8. `diff-top` is not informative here. In run B only one set exists up to the sweep (13590911: `windows=24;moving=3;changed-words=1216;table=62`) and the later one is frozen from 13605038 (`moving=7;changed-words=74588;table=2267`). All 10 ranks are `hits=1;misses=0;score=1` at `1f8a72e0000+3FAB284..3FAB594` (stride 0x70, `enc=fx4096/turn` ~2890-2896 or `deg` 582.3; offsets in the last 0.4 MiB of the 64 MiB region, far from `FDD410`). With every rank tied at score 1 the order is just insertion order. `FDD410` is not among them, and nothing in the log shows these words moving with the look (one hit each, 4 holds happened). No block was found by the diff that the scan missed. Run 4's top were at `+B4C4,+B7A4,+FA44,+13FB4` (`enc=rad`, max 2.00025), also `hits=1;score=1`; neither run gives a ranked input-word candidate. Do not treat either list as the look input.
9. The E6 start block is wrong in both runs (`1f873a00000`, run 4 `240537b0000`: all zero at `+FDD400`, `class=static`). Live EE is a different 64 MiB region (`1f8a72e0000`) found only by the full process scan (370-382 regions, about 3.7 s per scan, every 5 s, `scan_every_ms`). So the "fixed offset from a classified base" depends on the scan finding the base each time.

## Writer location logic: robust or not
- Established: base is derived structurally per launch (`eff = hit.offset - field_offset[look_yaw]`, ee_camera_probe.cpp:704/714), so ASLR-like movement of the region is handled; offset `0xFDD410` held in 2 of 2 launches (runs 4 and B) on 2 different DLL builds (step18, step29). All 14 fields at `FDD40C..FDD894` are in the same relative layout.
- Not established: other missions, game versions/discs, emulator builds. A mission change could move or re-initialise the block. There is no fingerprint beyond the relations; today a junk block would be accepted by the writer only via `tracks-look` evidence, which is good, but the lock is lost on a single miss, which is the real fragility.
- The writer can also start while the harness is still sweeping: the gate checks look-yaw neutral only; the settle began at 13589.9 with the up/down holds still to come (pitch is not checked in 2a), so a trial would have overlapped key input.

## Proposed bounded improvement (two small parts, no new hooks, read-only until validated)
A. Sticky identity (ee_camera_probe.cpp `set_tracks`, about 25 lines): do not evict a track that is `tracks-look` (lookEv>=2, hit>=60 %) or the current `bestEff_`/writer `locked_eff` unless it was absent from N=3 consecutive scans AND its own per-tick snapshot fails `relations` for >= 2 s. Do not change `observe-follow` unless the new best has score >= the current one (junk 4 can never replace a 5). Never let a score-4 entry without `rel_eye` be `best0` when a score-5 track exists. Keep per-track counters across a missed scan.
B. Cheap structural re-validation instead of relying on the 3.7 s scan: every timeline tick (250 ms) the probe already reads `read_snapshot(mem, c.eff)`. Add a locator that, for each private RW committed region of size 0x4000000 (a handful) reads the 14-word neighbourhood at `+FDD40C..FDD894` and applies `relations()` (tolerance widened to `2e-3 + 1.5 * |dL|` using the previous tick's L change, which is what the existing `extra_yaw` argument is for; double-read the words and use the pair with the smaller residual to avoid torn frames). Result: eff is re-confirmed in about 1 ms per tick, also during holds; the full scan remains the fallback and the discovery step only. Requires `rel_eye` (score 5) for lock; log region base, size and `eff-lo` for each lock.
C. Writer gate (ee_look_write.cpp): require the identity to be confirmed by B (not only the scan) for >= 2 s, look yaw AND pitch neutral for >= 2 s, and no look event in the last 2 s, so a trial cannot overlap a sweep.

## Read-only validation
1. Offline replay (no game): feed the 18 logged `scan-best` lists of run B and the 16 of run 4 into `set_tracks` with rule A; expect slot 0 stays `1f8a72e0000` through scan 4 and `look 13/13` instead of `0/4`. Add the three residuals above as `relations()` unit cases (fail with tolerance 2e-3, pass with `extra_yaw = 1.5*|dL|`).
2. One live read-only run on the null HMD, `ee_camera_probe` only, no writes, no skip-intro mod, normal route to cockpit, sweep as in run 4 but deliberately started right after a scan begins and repeated 3 times; keep the sweep while scans overlap it. Pass: the locked eff never changes across the sweeps, locator confirms FDD410 on >= 99 % of 250 ms ticks including holds, `tracks-look` with >= 12 events, no slot churn; count how often the strict 2e-3 test would have failed (expected: only during ramps) to size the tolerance.
3. Cross-launch/cross-mission: relaunch twice more (and once with the skip-intro mod) and log `region base`, `size`, `eff-lo` and the relations at `+FDD410`; pass if `eff-lo==0` and the 14-word relations hold each time. Optionally, find a fixed-address ASCII fingerprint (disc serial / ELF name) in the same region with a read-only dump to use as a build check (guess: such a string exists at a fixed offset; not yet looked for).

## Guessed / unverified
- That `FDD410` is a PS2 RAM address (consistent with `eff==lo`, but no emulator or ELF symbol evidence in these logs).
- That scan 4's miss is the yaw tolerance rather than a different failure (eye, sane); the dropped hit is not logged. A cheap fix is to log the best near-miss for the known offset each scan (`scan-probe;off=+FDD410;mask=...;yaw-res=...`).
- That tear (chunk read mid-frame) rather than ramp lag causes the residual; both are fixed by B.
